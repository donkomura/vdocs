## Project Overview

vdocs is a Chrome MV3 extension that brings Vim-style editing to Google Docs.
The Vim core (modes, key sequence parsing, command emission) is implemented in
Rust and compiled to WebAssembly via `wasm-bindgen` / `wasm-pack`. The browser
extension (JS, DOM, key events) consumes the Wasm module through a JSON
string-in / JSON string-out boundary.

## Language Conventions

  and JavaScript sources, including module-level doc comments and per-test
  rationale comments.
- **All commit messages must be written in English.**
- User-facing documentation (README, etc.) may remain in Japanese where it
  already is, but code-adjacent prose is English-only.

## Common Commands

Build the Wasm module into `extension/pkg/`:

```bash
make build
```

Clean build artifacts (`extension/pkg/` and `cargo clean`):

```bash
make clean
```

Run the full Rust test suite:

```bash
cargo test
```

Run a single integration test file:

```bash
cargo test --test wasm_api
cargo test --test parser_motion
cargo test --test parser_commands
```

Run a single test case by name:

```bash
cargo test --test wasm_api wire_format_of_move_command_is_stable
```

Load the extension in Chrome: open `chrome://extensions`, enable Developer
Mode, click "Load unpacked", and select the `extension/` directory. The
`extension/pkg/` output from `make build` must exist before loading.

## Architecture

### Rust/Wasm core (`crates/vim_core/`)

The core is a single `VimCore` struct exposed to JS via `wasm-bindgen`
(`src/lib.rs`). It has only two public methods:

- `on_key(key_json: &str) -> String` — accepts a JSON-encoded key event,
  returns a JSON-encoded array of `Command` values.
- `mode() -> String` — returns the current mode as `"normal"` or `"insert"`.

Both methods are **total**: malformed input never panics and yields `"[]"` or
the current mode string. Panicking at the Wasm boundary traps the content
script and kills all subsequent key handling, so the boundary must absorb
every error.

Internal modules:

- `parser.rs` — the key-sequence state machine. Holds `pending_count`,
  `pending_operator`, and `pending_g` state that survives across `on_key`
  calls. Produces `Vec<Command>` per key.
- `command.rs` — the `Command` enum and `Direction` enum. `Command` is
  serialized with `#[serde(tag = "type")]` so each variant becomes a tagged
  JSON object (e.g. `{"type":"Move","direction":"Down","count":1}`).
- `mode.rs` — the `Mode` enum (`Normal` / `Insert`) and its string mapping.

### Wire format (JS ↔ Wasm contract)

The JS side depends only on the JSON shape of `Command`, not on any Rust
internals. The shape is fixed by the integration tests in
`crates/vim_core/tests/wasm_api.rs`. When changing the `Command` enum or its
Serde attributes, these tests are the canonical contract — update them
deliberately, not incidentally.

### Chrome extension (`extension/`)

- `manifest.json` — MV3 manifest. `wasm-unsafe-eval` is in the CSP because
  Chrome 103+ requires it to instantiate Wasm. Permissions are limited to
  `storage` and `activeTab`, and content scripts only match
  `https://docs.google.com/document/*`.
- `content.js` — injected into Google Docs; forwards key events into
  `VimCore.on_key` and acts on the returned commands.
- `background.js`, `popup.html`, `popup.js` — service worker and toolbar UI.
- `pkg/` — generated by `make build`; do not edit by hand. Listed in
  `web_accessible_resources` so the content script can load the Wasm glue.

## Testing Discipline

This project follows test-driven development. Before writing a test, design
what *guarantee* the test encodes and state it at the top of the test. The
project uses a fixed taxonomy of guarantees (see the header of
`crates/vim_core/tests/parser_motion.rs`):

- **G1. Mapping** — input → output is state-independent.
- **G2. Mapping + state transition** — input produces output *and* moves the
  state machine.
- **G3. Eventual consistency** — only the final state of an operation
  sequence is asserted.
- **G4. Ordered output** — the per-step output sequence is asserted.
- **G5. Boundary safety** — malformed input must not panic.

Every test carries a one-line comment starting with its guarantee code
(`// G1.`, `// G2 + G4.`, etc.) explaining *why* it exists. When adding a
test, decide the guarantee first, then write the comment, then the
assertion. Do not add a test without a guarantee classification.

Integration tests live under `crates/vim_core/tests/`:

- `parser_motion.rs` — motion keys, counts, and `g`-prefix behavior.
- `parser_commands.rs` — non-motion commands (insert, delete, yank, paste,
  operators).
- `wasm_api.rs` — JSON wire-format contract at the `VimCore` boundary.
- `common/` — shared helpers (`feed`, `k`, `move_cmd`, `shifted`).

Unit tests live alongside source files in `crates/vim_core/src/`.
